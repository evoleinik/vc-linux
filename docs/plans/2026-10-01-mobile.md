# The browser build on phones, and loading programs on first use

**Type:** Decision doc
**Status:** built; node gates passed, real-device check pending
**Date:** 2026-10-01

## Goal

Eugene, 2026-10-01: "I think we'll need to adapt it to mobile browser/input more too. now it's
perfect on desktop". Also, Rogue takes the page from 1.6 MB to 2.9 MB compressed, and VZ Editor,

## Criteria

1. Every key VC needs is reachable on a phone: F-keys, arrows, Esc, Tab, Ins, Enter, Ctrl, Alt.
2. The screen stays as readable as it is now.
3. The first visit stays fast on a phone network.
4. The desktop page does not change.

## Decision — 2026-10-01

- In portrait on a touch device, a key pad sits under the unchanged screen: F1 to F10, the
  arrows, Esc, Tab, Ins, Enter, sticky Ctrl, Alt and Shift, and a button that opens the phone's
  keyboard. Taps act as mouse clicks, so VC's own key bar works too.
- VC loads first. GW-BASIC, bootLogo, Rogue and later programs download their translated code the
  first time DOS EXEC runs them.
- Order: after VZ Editor and Rogue merge, since all three change the web build.

### Loading and size

The main wasm uses Emscripten `MAIN_MODULE=2`, narrow Asyncify and an explicit shared CPU/runtime
ABI. VC.COM and VC.OVL stay in it. Each external image is an unchanged generated translation
compiled with `SIDE_MODULE=2`, without Asyncify. BASIC's graphics supplement travels with BASIC.
After a complete DOS-file byte match, EXEC awaits a build-stamped fetch into private MEMFS,
then `dlopen`/`dlsym` obtains its Image and runner. The side shares VC's memory and function table.
The downloaded module stays loaded for the session. Neither a filename guess nor viewing an EXE
loads its translation.

Both the fetch and Emscripten's `dlopen` suspend on the dispatcher's direct call chain; no wait
runs under `Image.run`. The node smoke withholds each first download across an event-loop turn
and verifies that VC's screen, input polling and output remain unchanged. It then runs and reruns
GW-BASIC, bootLogo, Rogue and VZ, requiring exactly one fetch per module. The binary gate checks
the actual wasm imports, exports and `dylink.0` metadata, including no eager library dependencies
and no Asyncify in any side.

The first-load gate follows the built page's resources, including transitive scripts, xterm,
CSS, the font and the main wasm. Each file is compressed separately with gzip level 9.

| Build | First-load bytes, gzip |
|---|---:|
| Before, monolithic (VC + BASIC + Logo + Rogue + VZ) | 3,803,040 |
| After, VC first and four lazy modules | 1,279,346 |
| Required maximum | 1,300,000 |

Level-6 gzip also fits: 1,285,653 bytes after, versus 3,860,138 before. The main wasm is
5,658,766 raw bytes / 1,127,711 gzip bytes. Lazy wasm gzip sizes are 492,562 (BASIC), 7,446
(bootLogo), 1,287,727 (Rogue) and 572,721 (VZ).

Plain PIC `-O2` produced a 1,354,511-byte gzipped main wasm; `-Os` produced 1,377,421 and
`-Oz` 1,155,030, still over budget once page assets were counted. The selected main-only flags
are `-O2 -fno-inline-functions -sMALLOC=emmalloc`: keeping generated helpers out of line beats
those variants without changing their source. Side programs keep ordinary `-O2`. A non-PIC
main was rejected by wasm-ld, and neither hidden visibility nor LTO gave a useful reduction.

Two integration failures now have regressions:

- A rejected request, HTTP 503, or malformed wasm returns DOS error 5. VC's saved user screen
  contains `Access denied`, F3 still works, and a later EXEC retries successfully. A fresh private
  staging path per attempt avoids Emscripten's stale internal entry after a failed `dlopen`.
- Loading all programs exceeded the old fixed 16 MiB heap. Memory growth is enabled; the smoke
  reaches 20,185,088 bytes and runs cached BASIC again after VZ to check the shared-memory path.

The failure smoke exercises the production `fetch` branch with a node-only Response double,
including refusing to read an HTTP-error body. The ordinary smoke uses asynchronous local reads.
The size gate and first-use smoke were observed failing against the original monolithic build.

### Portrait input and language

`web/vc-keypad.js` holds the pure input reducer and small DOM binding. Only the exact coarse-pointer
portrait query shows the pad. The screen fit calculation is unchanged. Sticky keys emit the same
kitty modifier events as hardware keys, apply once to a pad key or typed character, and preserve
physically held modifiers. Mouse reports remain mouse input. Unit tests cover all key bytes,
sticky on/off, media-query changes, keyboard focus and the unchanged fit budget. Additional
node checks against the real VC confirmed its modifier key bars and mixed mouse/keyboard input.

The footer and quit message select Russian for `ru`, Ukrainian for `uk`, and English otherwise.
The supplied Russian README is kept as UTF-8 source and packaged as 1,512 bytes of CP866/CRLF
under `H:\ПРОЧТИ.TXT`; the smoke opens it in VC's F3 viewer and checks the Cyrillic text.
Emscripten 4.0.2 cannot emit assembler symbols for that filename, so packaging uses an ASCII
staging name, renamed before DOS starts. Ukrainian remains on the Unicode page only.
Program binaries and definitions already installed from `gen/files.c` are excluded from the
startup MEMFS package so they are not downloaded twice.

At the Brief 21 handoff, remaining weaknesses were: downloads had no timeout/cancel (`runtime/web_programs.c:35`), pad keys
have no press-and-hold repeat (`web/vc-keypad.js:136`), and DOM doubles cannot verify actual
phone keyboard/zoom behavior (`tests/test_web_keypad.mjs:106`). Short portrait windows can
scroll to the controls rather than shrink the screen. The real-device check remains with Eugene.

### Memory and first load

The guard allows `2 * module_file_size + 65,536` bytes before `dlopen`: one retained raw copy,
one allowance for side statics/alignment, plus allocator/DSO/Asyncify bookkeeping. The binary
gate requires statics plus alignment to fit within one file size; actual static data is only
6.94–8.09% of the four file sizes. The guard counts current unclaimed and allocator-free memory,
then proves a contiguous region is available. Clang optimized away an initial unused
`malloc`/`free` probe, including its failure check; the fragmentation test caught that as DOS
error 5. Explicit `emmalloc_malloc`/`emmalloc_free` calls remain in optimized IR and pass it.

| Measurement | Bytes |
|---|---:|
| Previous normal-session linear-memory peak | 20,185,088 |
| Final allocator high-water after all four programs, including the contiguous probe | 26,030,552 |
| `INITIAL_MEMORY` / normal-session start and finish | 33,554,432 |
| Headroom over the final high-water | 7,523,880 |
| First load, separately gzip-compressed assets at level 9 | 1,280,032 |
| First-load limit | 1,300,000 |

The memory gate prints these values and requires no growth, at least 4 MiB headroom, and at least
20% headroom over the high-water. `sbrk(0)` measures the retained allocator arena high-water,
including statics and stack; this is not a measurement of total JavaScript/JIT process memory.
Removing the MEMFS staging file does not free Emscripten's retained raw heap copy, including
failed link attempts; the runtime comment now says so.

### Memory sized for any load order

The verification review found the measured peak depended on load order. emmalloc takes a whole new
block from sbrk when no free block fits, so BASIC, then VZ, then Rogue peaks higher than the tested
order. The gate now bounds every order as the startup heap top plus 2N + 64 KiB per module. At
32 MiB that bound left 681,762 bytes of headroom and the gate failed. `INITIAL_MEMORY` is now 48 MiB.
